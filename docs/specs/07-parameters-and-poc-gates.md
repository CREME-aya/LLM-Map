### 2.2 Gate 3 記録形式・監査・集計

- **記録ファイル**: `cases.ndjson` / `routes.ndjson` / `audits.ndjson`。`od_id` / `route_id` で結合する。Gate 3 の記録とハーネスの置き場所は `pipeline/harness/`（[02 §2](02-architecture-and-stack.md)）。

| ファイル | 必須列 |
|---|---|
| `cases.ndjson`（OD） | OD ID・地点・時刻・車両条件・データ版 |
| `routes.ndjson`（候補） | OD ID・候補 ID・探索結果・経路参照・標準/採用区分・入口表示 |
| `audits.ndjson`（監査） | 候補 ID・合法性・右折件数・狭路距離・入口方向・出典・未確認箇所 |

- **OD 結果行**: `routes.ndjson` には OD ごとの実行結果行を必ず 1 行置く（`ok` / `no_route` / `incomplete_data` / `timeout` / `error`）。**集計前に 40 件すべての結果行を検証** する。
- **40 OD 内訳**: 都市部対向横断右折 12・郊外狭路 12・目的地入口方向 8・山間/県境/離島 8。
- **監査**: 盲検で行い、判定が割れたら二人目が監査する。
- **タグ集計の分母**: 信号 = 車道交差点ノード、`width` / `lanes` = 道路区間（距離加重も併記）、`turn:lanes` = 流入方向。

### 2.3 Gate 4 計測系統・採点ルール

- **2 系統で記録**:
  1. **エンドツーエンド**: 初回応答時間・自然文候補提示時間・縮退率。コールド指標 **p95 ≤ 3 秒** または縮退率を追加。
  2. **SLM 単体**: 曖昧 30・否定 20・契約外 20 を SLM へ直接通す。
- **採点ルール**:

| 区分 | 件数 | 合格条件 |
|---|---|---|
| 明確 | 40 | 正解率 **≥ 90%**（分母は明確 40 件） |
| 曖昧 | 30 | 正しいコード / `NOOP` / 聞き返しなら合格。それ以外の操作実行は契約外実行 |
| 否定 | 20 | 期待コードか `NOOP` 以外は失敗 |
| 契約外 | 20 | 期待コードか `NOOP` 以外は失敗 |
| 雑音 | 10 | 明確な命令＋車内雑音。判定は曖昧と同じ安全判定（正しいコード / `NOOP` / 聞き返しなら合格、契約外実行 **0**） |

- **期待コード**: 録音前に 2 人で付けて固定する。期待命令コード表の正本は `schema/slm/expected_codes.json`、120 発話の評価データとハーネスは `pipeline/harness/`（命令コードは [03 §4.1](03-routing-and-two-layer-control.md)）。

### 2.4 Gate 7 共通テストデータ（探索競合）

探索キューと `search_finished` の仕様は [03 §3.1](03-routing-and-two-layer-control.md)。

```
t0 start{r1, avoid_chip} → Running{r1}
t1 fix: 逸脱検知 → cancel{r1}, ui: 経路を確認中
t2 search_finished{r1, ok} → 結果破棄・枠解放 → start{r2, reroute}
t3 search_finished{r2, ok} → 原子コミット・新 horizon
検証: 同時 Running ≤ 1 / r1 由来の表示・発話 0 / (t2−t1),(t3−t1) を記録
t3 の「原子コミット」は Rust の commit{r2, route_key} → Kotlin の dc_route_commit
派生: t2 が来ない → 監視期限超過を Rust が検出 → engine_stuck → 実際の戻り後 search_finished{r1}（ok でも discarded_after_stuck）→ 枠解放 → start{r2, reroute}
```

計画の外の探索の距離区分（[03 §3.1](03-routing-and-two-layer-control.md)）の境界ケース：
- 現経路の有効な残り ETA が 29:59 → `short`（監視上限 5 s）
- 30:00 → `long`（10 s）
- 直前の計画は `short` だったが、逸脱後に残り ETA が失効 → `long`（旧区分を引き継がない）

`commit` の版ずれ：`commit{r2, route_key}` を出した後、`dc_route_commit` を呼ぶ前に経路が差し替わる → `dc_route_commit` は `E_STALE`、遅れた経路由来の `horizon` 更新・発話 **0**

経路上の位置合わせ（[04 §3.1](04-maneuver-horizon-and-hmi.md)）の最初の確認ケース：長距離のチャンク境界（累積距離の連続）・並行道路（絞れないときは `uncertain`）・トンネル復帰（再捕捉）。通常走行と再捕捉を分けて、照合した線分数と `dc_tick` の p95・最大時間を記録する。

逸脱検出と並行道路のケース：
1. 本線から 20 m 離れて同じ向きに続く側道 → すぐには検出できないことを仕様どおりの動きとして記録する
2. 横のずれがちょうど 30 m（`lateral_tol_cm`）の境界値
3. 分岐した後 40 m まで離れていく側道 → 検出までにかかった Fix の回数を記録する
4. 本線の上で測位だけがぶれる（`acc_cm` が `max_acc_cm` を超える Fix を含む）→ 誤検出 **0**
5. 方位 359.996°（Kotlin の丸めで 0）と、範囲外の 36000（`E_SCHEMA` で拒否）
6. 有効な範囲外 Fix 2 回 → 精度の悪い Fix 2 回 → 有効な範囲外 Fix 1 回 → 最後の時点で逸脱カウントは 1、`reroute` の `start` は出ない
7. 有効な範囲外 Fix と精度の悪い Fix が交互に続く（実際には逸脱している）→ 逸脱が確定しないまま続くことを、検出の遅れ（経過時間と Fix 数）として記録する

### 2.5 Gate 4 / 7 共通: 提案差し替え系テスト（`pending_offer`）

確定入口と承認時の `target_id` 再検証は [03 §4.2](03-routing-and-two-layer-control.md)。以下の 3 ケースすべてで **経路変更 0・古い案内発話 0**。

| ケース | 内容 |
|---|---|
| 発話中に提案差し替え | 発話中に提案が差し替わっても承認を引き継がない |
| 承認直前に逸脱 | 承認直前に逸脱が起きる |
| 表示後に締切超過 | 提案表示後に締切を過ぎる |
